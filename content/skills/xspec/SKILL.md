# xspec

xspec 是简化的规格驱动开发流程。SPEC 客观描述产品当前能力和代码实现，开发时作为参考。每次开发在任务目录中临时记录计划和验收，完成后把实际实现合并回 SPEC，再删除任务目录。仓库最终只保留 SPEC，并以其为准。

## 调用

本次参数：$ARGUMENTS

- Claude Code 和 Devin 输入 `/xspec <命令> [参数]`，上一行会替换为实际参数。Codex 选择 `$xspec`，不替换上一行的占位符，此时取用户消息中 `$xspec` 之后的文字。
- Codex 也可以直接选择 `$xspec:scan`、`$xspec:plan` 或 `$xspec:sync`。这些入口已经指定命令，入口后的文字直接作为该命令的参数。
- Claude Code 也可以直接输入 `/xspec-scan`、`/xspec-plan` 或 `/xspec-sync`，用法同 Codex 的子命令入口。
- 参数的第一个词选择命令，其余文字是范围或任务描述。无命令或命令无法识别时执行 `help`。

| 命令 | 操作 |
| --- | --- |
| `scan [模块或路径]` | 按源码建立或复核项目总览、架构和模块 SPEC，与用户核对关键事实。省略范围时扫描全仓。 |
| `plan <任务描述>` | 确定任务类型和主责模块，创建任务目录，写入计划和验收标准，经用户确认后进入实施。 |
| `sync [模块/任务]` | 把任务的最终实现合并到 SPEC 并记录验收结果，任务完成后经用户确认删除任务目录。 |
| `help` | 显示本表、调用方式和示例，不读取仓库。 |

示例：`/xspec plan 修复换机后旧会话未失效`，实现后 `/xspec sync account-session/fix-device-takeover`。Codex 中写作 `$xspec:plan 修复换机后旧会话未失效`，Claude Code 中也可写作 `/xspec-plan 修复换机后旧会话未失效`。

## 通用规则

- 执行前读取项目约定（如 `AGENTS.md`）并核对 Git 工作树。保留已有暂存和未提交改动，与本命令无关的改动不纳入判断。
- 项目约定与本 skill 的布局或流程冲突时，先报告冲突点，由用户决定沿用项目约定还是修改约定。
- 已有工程文档（开发指南、接口契约、运行说明、测试证据等）覆盖的内容，在 SPEC 中链接引用，不复制。
- 规格文档随代码进入 Git，不写入秘密、真实用户数据、环境专用地址或云实例标识。
- xspec 只维护文档，不提交、不推送。业务实现按用户对当前开发任务的授权进行。
- 每个命令结束前检查本次涉及文档的链接、索引和关键断言，汇报新增、更新或删除的文档，以及仍待确认或待验证的事项。

## 文档布局

```text
specs/
├── SPEC.md                  项目总览（长期）
├── ARCHITECTURE.md          总体架构（长期）
└── <module>/
    ├── SPEC.md              模块规格（长期）
    └── tasks/<task>/        进行中的任务（临时）
        ├── PLAN.md
        └── ACCEPTANCE.md
```

- 项目总览说明当前能力、主要业务流程和模块索引。架构说明系统组件、依赖方向、运行入口、数据归属、跨模块流程和外部服务边界。模块 SPEC 说明模块的目的、职责、实现要点和业务流程。
- 项目约定可以指定文档位置，例如项目总览放在仓库根目录 `SPEC.md`。按约定位置读写，未指定的部分沿用上图。
- 任务目录只在开发期间存在，目录存在即表示任务未完成。`PLAN.md` 记录目标、范围、现状、实施思路和受影响模块。`ACCEPTANCE.md` 逐项记录验收标准与实际结果。
- 以稳定的业务或技术职责划分模块，一份模块 SPEC 可以覆盖多端或多个源码目录。模块和任务用小写英文短名，以连字符分词。模块名表达职责，任务名以任务类型开头，后接改动目标。
- 跨模块任务归主责模块，其他受影响模块写入计划。同一模块下已有同名任务时，继续该任务或换用更具体的名称。
- 新建文档时读取本 skill 目录下 `references/templates/` 中的对应模板：`project-spec.md`、`architecture.md`、`module-spec.md`、`plan.md`、`acceptance.md`。更新已有文档时沿用其结构。

## 事实依据

- 从实际注册的入口和调用链核对行为，结合配置、持久化、迁移和相关测试判断生效条件。
- 核心结论附近给出可复查的依据。文件链接写相对当前文档的路径，例如从 `specs/<module>/SPEC.md` 指向 `../../backend/...`。依据定位到符号或测试名，不写行号。
- 模块目的写可观察的职责。技术取舍和业务意图以可查证的记录或用户确认为依据。用户确认的目标与实现有差异时，说明差异和证据。
- SPEC 只写当前实现：关键机制、不变量、状态、权限、数据变化和失败处理，不逐行复述代码。待实现行为只写在任务的计划和验收中。
- 写清证据范围。代码证明实现路径，测试只证明其实际覆盖范围，特定环境的启用和运行结果由该环境的证据支持。尚未确认的结论标为“待确认”，并说明确认方式。

## 任务生命周期

状态写在 `PLAN.md` 开头。

| 状态 | 进入条件 | 后续 |
| --- | --- | --- |
| `草案` | `plan` 写入计划 | 用户确认类型、计划和验收标准 |
| `实施中` | 用户确认计划 | 按计划实现。范围变化时同步修改 `PLAN.md` 和 `ACCEPTANCE.md`，验证结果随时记入 `ACCEPTANCE.md` |
| `待收尾` | `sync` 已合并实现，仍有验收项失败、未运行或受阻 | 补齐验证或由用户接受缺口后，再次 `sync` |
| 完成 | 验收全部通过，或用户接受剩余缺口 | 经用户确认后删除任务目录 |

两份任务文档的模板自带使用说明。实现阶段不调用 xspec 时，也按其记录状态和验证结果。

## 任务类型

每个任务有一个类型，写在 `PLAN.md` 开头。类型与 Conventional Commits 一致，提交时可以沿用。

| 类型 | 适用 | `PLAN.md` 必须写 | 验收必须包含 | 合并回 SPEC |
| --- | --- | --- | --- | --- |
| `feat` | 新增、修改或移除可观察行为 | 变化的行为、入口、权限和数据。移除时写明退役的入口和数据处理 | 变化后的可观察结果。移除时包含原入口不再可用 | 新增、修改或删除行为说明，必要时新建或退役模块 |
| `fix` | 实际行为偏离已确认的预期 | 复现步骤、预期与实际、根因 | 原复现场景通过。能补回归测试时，记录其修复前失败、修复后通过 | 修正行为说明，移除已解决的“已知限制” |
| `refactor` | 不改变可观察行为的结构或性能调整 | 保持不变的行为清单。性能调整写指标和测量方法 | 行为不变的证据。性能调整附前后指标 | 只更新实现要点和架构，行为说明不变 |

- `feat` 和 `fix` 可以包含必要的重构。`refactor` 不得改变可观察行为，实施中出现行为变化时，停下请用户决定拆分任务或改变类型。
- 一个任务只有一个类型。目的混合时按主要目的归类，或拆成多个任务。
- 不改变 SPEC 所述行为的文档、构建、格式和纯测试改动，不需要建立任务。

## `scan [模块或路径]`

1. 盘点范围内的应用入口、业务模块、支撑模块、后台任务和数据边界，从代表性入口追踪主路径及影响结论的失败分支。省略范围时扫描全仓。
2. 按模块与用户核对。先给出查到的行为和依据，再提出影响职责、业务规则或边界判断的问题。大型仓库分批核对。
3. 创建或更新项目总览、架构和模块 SPEC，连通索引和引用。在项目总览的模块索引中记录每个模块的核对状态（已核对、待核对、有待确认项），下次 `scan` 从未完成的模块继续。
4. 已有规格文档不在约定位置时，向用户确认迁移范围后再迁入，并修正原有引用。
5. 代码在 xspec 流程之外发生变化时，用 `scan <模块>` 复核并修正对应 SPEC。

## `plan <任务描述>`

1. 缺任务描述时询问要建立的任务。
2. 读取相关模块 SPEC 和代码，确定任务类型、主责模块与任务名。描述以 `feat:`、`fix:` 或 `refactor:` 开头时直接采用该类型，否则从描述推断。模块尚无 SPEC 时直接核对相关代码，在计划中注明缺口，不触发全仓扫描。
3. 按模板创建 `PLAN.md` 和 `ACCEPTANCE.md`，状态为 `草案`，基线记录当前 `HEAD` 的提交号。按任务类型写入必需内容和必需的验收条目。验收标准写可观察结果，各项初始状态为 `未运行`。
4. 展示任务类型、计划摘要和任务路径，请用户确认或修改。确认后把状态改为 `实施中`。用户在本次调用中要求直接实现时，确认计划后继续实现，否则到此结束。

## `sync [模块/任务]`

1. 选择任务。使用参数指定的任务。省略时优先当前对话中已明确的任务，否则查找现有任务目录：只有一个时直接使用，有多个时请用户选定。
2. 确定实际改动。对比 `PLAN.md` 记录的基线与当前工作树（含已提交和未提交改动），只取属于本任务的部分。实现与计划有偏差时以实际实现为准，在汇报中列出偏差。
3. 合并到长期文档：
   - 职责、实现要点或流程变化时更新受影响的模块 SPEC。
   - 新增独立模块时创建 SPEC 并加入索引。模块合并或退役时更新归属，移除失效的模块说明并修正引用。
   - 跨模块依赖、数据归属或运行边界变化时更新架构。项目能力变化时更新项目总览。
   - 按任务类型的合并规则执行。`refactor` 任务的实际改动改变了可观察行为时，作为偏差报告，由用户决定拆分任务或改变类型。
   - 未实现或未达成的计划内容不写入 SPEC。
4. 记录验收。在 `ACCEPTANCE.md` 逐项填写验证方式、结果和证据，状态取通过、失败、未运行或受阻。核对任务类型要求的验收条目齐全。只采用已有证据：实现过程中的记录、本次会话中的运行结果、可查证的测试和报告。缺少证据时列出建议的检查，由用户决定是否运行。
5. 收尾。验收全部通过，或用户接受剩余缺口时：
   - 把影响当前行为判断的已接受缺口写入模块 SPEC 的“已知限制”。
   - 项目约定要求长期保留的验证证据，转入约定位置。
   - 列出将删除的任务目录，经用户确认后删除。

   其他情况把状态改为 `待收尾`，汇报待补的验收项。
6. 改动未经 `plan` 时，请用户指明改动范围（提交范围或当前未提交改动），据此合并到 SPEC，不补建任务目录，并在汇报中列出验证缺口。
